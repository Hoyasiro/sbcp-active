# 삼복출프 (SBCP) 서비스 기획서

> 이 문서는 실제 구현된 동작을 기준으로 작성했습니다.
> 설계 단계에서 정했으나 이번 범위에서 구현하지 않은 항목은 **[향후 과제]** 로 표시했습니다.

**운영 형태** — 학원 PC 한 대에 설치해 쓰는 로컬 프로그램 (처음: `SBCP_Setup_v<버전>.exe`, 업데이트: `SBCP_Update_v<버전>.exe`, 사용법은 `docs/사용설명서.md`)

---

## 1. 서비스 개요

| 항목 | 내용 |
|---|---|
| 서비스명 | 삼복출프 (SBCP) |
| 한 줄 정의 | 학생이 직접 체크한 출결을 자동 집계하고, AI가 주간 리포트 문장으로 옮겨 주는 학원 관리 서비스 |
| 형태 | 학원 PC에 설치하는 단일 HTML 프로그램. 브라우저로 열고, 데이터는 브라우저 저장소 + JSON 백업 파일로 관리. 인터넷은 AI 문장 생성에만 사용 |

### 목적

소규모 학원 원장이 매주 학부모에게 보낼 출결 리포트를 손으로 작성하는 부담을 줄이는 것입니다.

출결 기록 자체는 이미 쌓이고 있지만, 그 숫자를 "이번 주 민준이는 4일 출석했고 꾸준히 나오고 있습니다" 같은
문장으로 바꾸는 일은 사람이 매번 해야 합니다. 학생 수가 늘수록 이 작업이 부담이 됩니다.

이 서비스는 **숫자를 문장으로 옮기는 부분만** AI에게 맡깁니다.

### 해결하려는 문제

| 문제 | 해결 방식 |
|---|---|
| 원장이 출결을 일일이 입력해야 함 | 학생이 2자리 번호로 직접 체크 |
| 출석률·연속 출석을 손으로 계산 | 코드가 자동 집계 |
| 리포트 문장을 매주 새로 작성 | AI가 집계 결과를 문장으로 변환 |
| 학부모용과 학생용 표현이 다름 | 톤 2종 선택 지원 |
| 누구에게 언제 보냈는지 알 수 없음 | 발송 이력 자동 기록 |
| 학생이 자기 출결을 돌아볼 계기가 없음 | 지난주 리포트를 다음 주 등원 때 보여 주고, 친구들과 보드로 공유 |

## 2. 타겟 사용자

### 주 사용자 — 소규모 학원 원장

- 학생 수 약 40명 규모, 별도 행정 인력이 없음
- 학부모 소통을 중요하게 생각하지만 시간이 부족함
- 복잡한 관리 프로그램을 배울 시간이 없음

### 부 사용자 — 학원 학생

- 등·하원 시 체크인 화면만 사용
- 조작은 **2자리 번호 입력 한 번**으로 끝남
- 출결 랭킹을 통해 꾸준히 나오려는 동기를 얻음
- 등원할 때 **지난주 나의 리포트**를 보고, 출결 데스크 보드에서 **친구들의 지난주 리포트**를 보며 자극을 받음

### 간접 수신자 — 학부모

- 서비스에 직접 접속하지 않음
- 원장이 생성한 리포트를 메시지로 전달받음

> 초기 기획에서는 카카오톡 자동 발송을 검토했으나, 사업자 심사가 필요해 이번 범위에서 제외했습니다.
> 대신 리포트에 **복사하기 버튼**을 두어 원장이 원하는 경로로 보낼 수 있게 했습니다.

## 3. 페이지 구성

단일 페이지 안에서 5개 화면을 전환하는 방식입니다. 사이드바(모바일에서는 하단 탭바)로 이동합니다.

| # | 화면 | 사용자 | AI | 주요 기능 |
|---|---|---|---|---|
| 1 | 출결 데스크 | 학생 | ⭕ | 번호 입력으로 등·하원 체크, 오늘 출결 현황, 랭킹 TOP 3, **지난주 리포트 보드** |
| 2 | 학생 관리 | 원장 | ✕ | 학생 등록·수정·삭제 |
| 3 | 데이터 관리 | 원장 | ✕ | CSV 다운로드 3종, 전체 백업·복구, 리포트 발송 이력 |
| 4 | **주간 리포트** | 원장 | **⭕** | 주간 집계 + AI 리포트 생성 + 최근 이력 + 지난주 리포트 자동 생성 현황 |
| 5 | 설정 | 원장 | ✕ | 학원 정보, 휴원일 관리, 화면 테마 |

### 화면 이동 방식

- 데스크톱: 좌측 고정 사이드바
- 모바일(768px 이하): 하단 고정 탭바로 전환
- 페이지 새로고침 없이 화면만 교체 (`goTab()`)

## 4. 핵심 기능

### 4-1. 출결 체크 (화면 1)

학생이 2자리 번호를 입력하면 상태에 따라 자동으로 처리됩니다.

```
1회 입력 → 등원 처리
2회 입력 → 하원 처리
3회 입력 → "오늘 등/하원이 모두 완료되었습니다" 안내
```

**예외 처리 3종**

| 상황 | 처리 |
|---|---|
| 하원 체크를 잊음 | 출석·연속 출석은 인정, 체류 시간만 0분 |
| 잘못 입력 | 6초간 "취소하기" 토스트 표시 |
| 미등록 번호 | "등록되지 않은 번호입니다" 안내 |

### 4-2. 자동 집계 (화면 1·4)

- 월간 출결일수, 연속 출석일, 최장 연속 기록, 당월 체류 시간
- 항목별 랭킹 TOP 3 (월간 출결 / 최장 연속 / 당월 체류)

### 4-3. 휴원일 관리 (화면 5)

공휴일과 자체 휴강일을 등록하면 출석률 계산의 분모에서 제외됩니다.

- 양력 고정 공휴일 8종은 "올해 공휴일 한 번에 등록" 버튼으로 일괄 추가
- 음력 공휴일(설날·추석·부처님오신날)과 대체공휴일은 원장이 직접 등록

> 음력 공휴일은 계산이 복잡하고, 대체·임시 공휴일은 정부 발표 전에 알 수 없어
> 자동 등록 대상에서 제외했습니다.

### 4-4. 데이터 백업·복구 (화면 3)

모든 데이터를 JSON 파일로 내보내고 다시 불러올 수 있습니다.
브라우저 localStorage에 저장되므로, 기기를 옮기거나 브라우저 데이터가 초기화될 때 필요합니다.

- 백업 파일명에 날짜를 붙입니다 (`acad_backup_YYYY-MM-DD.json`)
- 복구 전에 파일을 검사해 원인별로 안내합니다 (확장자, JSON 손상, 학생 명단·출결 누락, 저장 실패)
- 덮어쓰기 전 확인 창에 학생 수·출결 기간을 보여 주고, 직전 데이터를 한 벌 보관합니다
- 사용 방법과 오류별 해결은 사용설명서(docs/사용설명서.md) 5절에 정리했습니다

### 4-5. 리포트 발송 이력 (화면 3·4)

AI가 생성한 리포트를 시각과 함께 누적 기록합니다. 자세한 설계는 8절에 있습니다.

### 4-6. 지난주 리포트 — 자동 생성 · 등원 팝업 · 친구 보드 (화면 1·4)

> 2026-09-30 추가. 외부 알림(카카오톡 등) 연동은 시간·역량상 보류하고,
> 리포트를 **학생이 학원 안에서 직접 보는 방식**으로 방향을 바꿨습니다.
> 목적은 친구들의 기록을 서로 보며 생기는 경쟁심으로 출석 의지를 높이는 것입니다.

**자동 생성** — 원장이 버튼을 누르지 않습니다.

| 항목 | 기준 |
|---|---|
| 대상 기간 | 지난주 월~금 운영일 |
| 대상 학생 | 지난주 운영일이 있고, 1일 이상 출석한 학생 |
| 1차 시도 | 평일 13:30 (데스크 PC가 켜지는 시각) |
| 2차 시도 | 평일 14:00 — 1차에서 실패·누락된 학생만 |
| PC를 늦게 켠 경우 | 켜진 직후 1차, 끝나는 대로 2차가 이어서 실행 |
| 호출 방식 | 한 명씩 순서대로 (동시 호출로 인한 제한·과금 폭주 방지) |
| 네트워크 단절 | 즉시 중단하고 다음 시도 시각에 다시 시도 |
| 비상 수단 | 주간 리포트 화면의 "미생성분 지금 생성" 버튼 |

**노출 규칙**

- 등원하면 기록 팝업에 **지난주 나의 리포트**(등급·출석·연속·평균 체류 + AI 한마디)가 함께 뜹니다
- 리포트가 생성되기 전에 등원한 학생은 그날은 **통계만** 보고, AI 한마디는 다음 등원 때부터 봅니다
- 지난주 출석 0일인 학생은 등급을 드러내지 않고 응원 문구만 보여 줍니다
- 지난주가 전체 휴원(운영일 0일)이면 휴원 안내 문구를 보여 줍니다

**친구 보드 (출결 데스크)**

| 항목 | 기준 |
|---|---|
| 표시 | 한 번에 3명. 세 카드가 칸 높이를 똑같이 나누고, AI 문장 글자 크기(13~24px)를 칸에 맞춰 자동 조절 |
| 순환 | 4초마다 한 칸씩 위로 (한 명이 약 12초 노출). 3명 이하면 순환하지 않음 |
| 수동 조작 (v1.7) | ‹ › 화살표로 한 칸씩 이동(4초 다시 셈), ❚❚ 일시정지 → ▶ 남은 초 표시, 10초 뒤 자동 재생(멈춘 중 화살표를 누르면 10초 다시 셈). 버튼 사용 후 번호 입력칸으로 초점 복귀 |
| 순환 대상 | 지난주 1일 이상 출석한 학생 (0일인 학생은 공개 순환에서 제외) |
| 친구 선택 | 드롭다운으로 고른 친구를 맨 위에 고정(분홍 테두리), 나머지 두 칸은 순서상 다음 친구 |
| 자동 복귀 | 선택 후 20초가 지나면 다시 전체 순환 (공용 PC에 고정된 채 방치 방지) |
| 입력 보호 | 드롭다운을 쓴 뒤 번호 입력칸으로 포커스가 돌아감 |

### 4-7. 화면 테마 (화면 5)

라이트/다크 모드를 전환할 수 있습니다. 선택은 저장되어 다음 접속에도 유지됩니다.

## 5. 판정 기준 정의서

주간 리포트의 집계와 등급 판정 기준입니다. 이 표가 곧 `weeklyStats()` 함수의 명세입니다.

### A. 기간

| 항목 | 기준 |
|---|---|
| 대상 기간 | 월~금 |
| 주 시작 | 월요일 |
| 운영 요일 | 월·화·수·목·금 |
| 제외 대상 | 주말, 등록된 휴원일 |
| 분모 | 그 주의 실제 운영일수 |

### B. 출석 비율 — 주 지표

| 등급 | 기준 |
|---|---|
| 최고 | 100% |
| 양호 | 80% 이상 |
| 보통 | 60% 이상 |
| 주의 | 60% 미만 |

### C. 연속 출석 — 보조 지표

| 항목 | 기준 |
|---|---|
| 계산 방식 | 주말과 등록된 휴원일을 건너뛰고 연속 유지 (직전 운영일에 출석했으면 +1) |
| 우수 기준 | 10일 이상 |
| 끊김 | 리포트에서 언급하되 질책하지 않는 톤 |
| 신기록 | 강조 |

> 휴원일을 추가·삭제하면 전체 학생의 연속 기록을 원본 출결에서 다시 계산합니다. (2026-09-30 반영)
> 지난주 리포트의 연속 출석은 "지난주 마지막 운영일 기준" 값을 사용합니다.

### D. 체류 시간 — 보조 지표

| 항목 | 기준 |
|---|---|
| 계산 | (하원 시각 − 등원 시각)의 그 주 평균 |
| 하원 미체크 | 0분으로 계산하되 평균에 포함 |
| 초과 체류 | 리포트에서 칭찬으로 언급 |

**0분을 평균에 포함하는 이유** — 하원 체크도 학생이 익혀야 할 습관이라고 보았습니다.
누락을 평균에서 빼면 체크를 안 하는 편이 유리해지기 때문입니다.

> **[향후 과제]** 다음 항목은 설계에는 포함했으나 구현하지 않았습니다.
> - 정상 체류 기준 시간(60분)의 설정 기능
> - "평소 대비 짧음" 판정 (지난 4주 평균과 비교)

### E. 최종 등급

**등급은 출석 비율로만 결정합니다.**

| 등급 | 조건 |
|---|---|
| 최고 | 출석률 100% |
| 양호 | 출석률 80% 이상 |
| 보통 | 출석률 60% 이상 |
| 주의 | 출석률 60% 미만 |

연속 출석과 체류 시간은 **문장의 재료로만 사용**하며 등급에 영향을 주지 않습니다.

**그렇게 정한 근거** — 체류 시간은 하원 체크 누락에 취약해 세 지표 중 신뢰도가 가장 낮습니다.
학생이 하원 체크를 잊으면 실제로는 오래 있었는데도 0분으로 기록됩니다.
신뢰도가 낮은 값이 등급을 흔들면 리포트 전체의 설득력이 떨어진다고 판단했습니다.

> **[향후 과제]** 초기 설계에서는 "최고" 등급에 연속 출석 조건
> (10일 이상 또는 신기록)을 추가로 요구했으나, 등급 판정을 출석률 한 가지로
> 단순화하는 편이 기준을 설명하기 쉽다고 판단해 구현에서 제외했습니다.

### F. 예외 처리

| 상황 | 화면 동작 | AI 호출 |
|---|---|---|
| 번호 미입력 | 생성 버튼이 표시되지 않음 | 없음 |
| 미등록 번호 | "등록되지 않은 번호입니다. 다시 한 번 확인해주세요." | 없음 |
| 이번 주 출결 기록 0건 | "이번 주 출결 기록이 없습니다. 출결 현황 기록을 확인해주세요." | 없음 |
| 과거 데이터 부족 | 체류 시간 비교를 생략하고 나머지만 생성 | 있음 |
| 신입생 | 주차별로 독립 계산. 주 중간 등록 시 다음 주부터 정상 집계 | 있음 |
| 한 주 전체 휴원 (운영일 0일) | "이번 주는 전체 휴원(운영일 0일)이라…" 안내 (지난주 보드·팝업도 휴원 안내) | 없음 |

## 6. AI 기능 설계

### 6-1. 설계 원칙 — 판정은 코드, 문장은 AI

> **판정까지는 JavaScript, 판정 결과를 글로 옮기는 것만 AI.**

같은 출결 데이터로 리포트를 몇 번을 생성하든 등급이 달라지면 안 됩니다.
학부모에게 보내는 문서이므로 일관성이 신뢰의 전제입니다.

그래서 출석률 계산과 등급 판정은 전부 코드가 처리하고,
AI에게는 **확정된 등급과 숫자를 넘겨 문장만 쓰게** 했습니다.

프롬프트에 명시한 규칙입니다.

- 등급은 이미 정해져 있다. 절대 다시 판단하지 마라
- 숫자를 지어내지 마라
- 주어진 정보에 없는 이름·사실을 지어내지 마라

> 세 번째 규칙은 처음부터 있던 것이 아니라, 테스트 중 AI가 입력에 없는 학생 이름을
> 만들어 낸 사례를 발견하고 추가한 것입니다.

### 6-2. 입력

**사용자가 제공하는 것**

| 항목 | 형식 | 필수 |
|---|---|---|
| 학생 번호 | 2자리 숫자 | ⭕ |
| 리포트 톤 | 학부모 발송용 / 학생 열람용 | ⭕ (기본값: 학부모 발송용) |

**코드가 AI에게 넘기는 것** (`buildReportData()`)

```
학생 이름: 김민준
레벨: Lv.5
기간: 2026-08-31 ~ 2026-09-04 (운영 5일)
출석: 4일 / 5일 (80%)
연속 출석: 4일 (최장 기록 4일)
평균 체류 시간: 121분
등급: 양호
하원 체크 누락: 1회
```

등급이 이미 확정된 상태로 전달되는 것이 핵심입니다.

### 6-3. 출력

**사용자에게 제공하는 가치** — 그대로 복사해 학부모에게 보낼 수 있는 완성된 문장

| 톤 | 대상 | 특징 |
|---|---|---|
| 학부모 발송용 | 학부모 | 존댓말, 학원의 관리 의지를 함께 전달 |
| 학생 열람용 | 학생 본인 | 격려 중심, 이해하기 쉬운 표현 |
| 지난주 보드용 (`peer`) | 학원 친구들 (공개) | 2~3문장, 친근한 존댓말, **비교·질책 금지**, 이번 주 목표 한 가지 응원 |

출력 예시 (학부모 발송용, 등급 "양호")

> 이번 한 주 동안 김민준 학생은 Lv.5 과정에 성실히 참여하였으며, 출결 등급은 '양호'입니다.
> 전체 운영일 5일 중 4일 동안 출석하여 80%의 출석률을 기록하였고,
> 평균 121분 동안 학원에 머물며 학습에 집중하였습니다. (이하 생략)

화면에는 리포트 문장과 함께 **복사하기 버튼**이 표시됩니다.

### 6-4. AI 호출 방식

서버 없이 **브라우저(HTML 파일)에서 Gemini API를 직접 호출**합니다. (`callReportApi()`)
Gemini는 로컬 파일(`file://`)에서 오는 요청도 허용하므로, 설치한 HTML 파일만으로 AI 문장을 만들 수 있습니다.

```
POST https://generativelanguage.googleapis.com/v1beta/interactions
헤더  x-goog-api-key: (설정 화면에서 등록한 키)
본문  { model, system_instruction: 톤별 프롬프트, input: 출결 요약 텍스트,
        generation_config: { thinking_level: "low" } }

함수 반환  { ok: true,  text: "리포트 문장" }
          { ok: false, error: "사용자에게 보여줄 안내 문구" }
```

| 항목 | 기준 |
|---|---|
| 키 보관 | 설정 → AI 연결에서 등록. 출결 DB와 **분리된** 저장소(`acad-gemini-key`)에 두어 **백업 파일에 포함되지 않음** |
| 키 표시 | 화면에는 끝 4자리만 표시 |
| 타임아웃 | 25초 (AbortController) |
| 성공·실패 형태 | 같은 모양으로 반환해 화면 쪽 분기를 단순화 |

> 초기(미션) 버전은 Vercel 서버리스 함수(`api/report.py`)가 키를 숨긴 채 대신 호출했습니다.
> 학원 PC 전용으로 전환하면서 서버를 없애고 직접 호출로 바꿨습니다. (2026-10, v1.5)

### 6-5. 실패 처리 기준

| 상황 | 화면에 표시되는 것 | API 호출 |
|---|---|---|
| 번호 미입력 | 생성 버튼이 나타나지 않음 (`rc-name`에 "번호를 입력하세요") | 없음 |
| 미등록 번호 | "등록되지 않은 번호입니다. 다시 한 번 확인해주세요." | 없음 |
| 이번 주 기록 0건 | "이번 주 출결 기록이 없습니다. 출결 현황 기록을 확인해주세요." | 없음 |
| **응답 지연** | 버튼이 "작성 중..."으로 바뀌고 "AI가 리포트를 작성하고 있습니다" 표시 | 진행 중 |
| **네트워크 끊김** | "연결에 실패했습니다. 네트워크 상태를 확인해 주세요." | 실패 |
| **키 오류 (400/401/403)** | "AI 키가 올바르지 않거나 사용할 수 없습니다. 설정 → AI 연결에서…" | 실패 |
| **사용량 제한 (429)** | "AI 사용량이 많아 잠시 막혔습니다…" | 실패 |
| **AI 서버 혼잡 (5xx)** | "AI 서버가 혼잡합니다. 잠시 후 다시 시도해 주세요." | 실패 |
| 키 미등록 | "AI 키가 등록되지 않았습니다. 설정 → AI 연결에서…" (지난주 자동 생성은 키 등록 전까지 대기) | 없음 |

**빈 입력 처리를 "안내"가 아닌 "차단"으로 바꾼 이유**

초기 구현은 버튼을 누르면 "학생 번호를 입력해 주세요" 메시지를 띄우는 방식이었습니다.
이후 유효한 번호가 입력되기 전에는 버튼 자체를 숨기도록 변경했습니다.
사용자가 실패를 경험한 뒤 안내받는 것보다, 애초에 실패할 수 없게 만드는 편이 낫다고 판단했습니다.
단, Enter 키 경로가 남아 있으므로 입력 검증 코드는 그대로 유지했습니다.

**에러 문구 분리 원칙**

외부 API의 원문 에러 메시지는 화면에 노출하지 않습니다.
에러 메시지에 키 일부가 섞여 나올 수 있기 때문입니다.
개발자용 상세 원인(HTTP 상태 코드)은 `console.error()`로만 남깁니다.

### 6-6. API 호출 최소화 설계

AI API는 호출마다 과금이 발생하고 응답에 20초 이상 걸립니다.
불필요한 호출을 네 겹으로 차단했습니다.

| 상황 | 호출 | 방법 |
|---|---|---|
| 빈 입력 · 미등록 번호 | ✕ | 버튼 숨김 + 입력 검증 |
| 이번 주 기록 0건 | ✕ | 집계 결과로 사전 판단 |
| 같은 조건 재요청 | ✕ | 2단 캐시 |
| 요청 중 버튼 연타 | ✕ | 버튼·입력칸 잠금 |
| 데이터 또는 톤 변경 | ⭕ | 캐시 키가 달라짐 |

**캐시 키 설계**

```
키 = 학생ID | 주 시작일 | 출석일 | 운영일 | 연속 | 평균체류 | 등급 | 톤
```

집계값을 전부 키에 넣었기 때문에, 학생이 추가로 출석하면 키가 달라져 자동으로 새 리포트가 생성됩니다.
데이터가 바뀌었는데 이전 리포트를 보여 주는 상황을 막기 위한 설계입니다.

저장은 메모리와 localStorage 양쪽에 하고, 학생·톤 조합당 최신 1건만 유지합니다.
집계값이 바뀌면 이전 리포트는 다시 쓰일 일이 없기 때문입니다.

**그 외 과금 대응**

- 외부 API 호출에 타임아웃 25초 지정
- `thinking_level`을 `low`로 고정 (동일 조건 비교 실험 후 결정)
- 자동 재시도 없음

## 7. 데이터 구조

```
DB {
  students   [ {id, no, name, level} ]
  attendance { "날짜": { "학생ID": {inTime, outTime} } }
  stats      { "학생ID": {currentStreak, longestStreak, lastAttendDate,
                          monthly, monthlyMinutes} }
  holidays   [ "날짜" ]
  settings   { academyName, phone }
  weekly     { reports: { "지난주 월요일": { "학생ID": {text, at} } },
               tries:   { "이번주 월요일": { "13:30": "시도 시각", "14:00": "..." } } }
}
```

별도 저장 항목

| 키 | 용도 | 갱신 방식 |
|---|---|---|
| `acad-report-cache` | 리포트 재사용 캐시 | 학생+톤 조합당 1건, 덮어씀 |
| `acad-report-history` | 리포트 발송 이력 | 누적, 최대 1,000건 |
| `acad-theme` | 화면 테마 선택 | 덮어씀 |

`weekly`는 최근 8주만 보관하며, DB 안에 있으므로 전체 백업·복구에 함께 포함됩니다.

`attendance`가 원본이고, `stats`는 빠른 조회를 위해 미리 계산해 둔 요약입니다.
둘이 어긋날 수 있으므로 `recalcStatsForStudent()`로 원본에서 요약을 다시 만들 수 있게 했습니다.

> 주간 리포트의 집계는 `stats`가 아니라 `attendance` 원본을 직접 읽어 계산합니다.
> 요약값의 오차가 리포트에 반영되지 않도록 하기 위함입니다.

## 8. 보너스 구현

### 8-1. 리포트 발송 이력 (운영 자동화 / 데이터 저장 고도화)

**목적** — 기존에는 리포트를 생성해도 화면을 벗어나면 사라졌습니다.
"이번 달에 누구에게 몇 번 리포트를 보냈는가"를 확인할 수 없었습니다.

| 항목 | 내용 |
|---|---|
| 저장 대상 | 생성 시각, 학생 번호·이름, 톤, 등급, 출석률, 기간, 리포트 전문 |
| 저장 위치 | localStorage (`acad-report-history`) |
| 보관 상한 | 1,000건 (초과 시 오래된 것부터 자동 제외) |
| 표시 | 주간 리포트 화면 최근 5건 / 데이터 관리 화면 최근 50건 |
| 내보내기 | CSV 다운로드 (표시 제한과 무관하게 전체 기록 포함) |

**캐시와 저장소를 분리한 이유**

| | 캐시 | 이력 |
|---|---|---|
| 목적 | 같은 조건이면 재사용 | 언제 무엇을 만들었는지 기록 |
| 보관 | 조합당 1건, 덮어씀 | 누적 |
| 키 | 집계값 조합 | 생성 시각 |

캐시 기준으로 이력을 관리하면 집계값이 바뀔 때 기록이 사라지므로 함께 둘 수 없었습니다.

**보관 상한 결정 근거** — 학생 40명 기준 주당 약 40건이 쌓입니다.
처음 잡았던 100건은 2.5주치에 불과해 이력으로서 의미가 없었고,
1,000건으로 상향해 약 6개월치를 확보했습니다.
항목당 700바이트 남짓이라 전체 0.7MB 수준으로, 출결 데이터와 함께 써도 여유가 있습니다.

**표시와 저장을 분리한 이유** — 1,000건을 한 번에 그리면 렌더링이 느려지고
스크롤이 무의미하게 길어집니다. 화면에는 필요한 만큼만 표시하고,
전체 조회는 CSV 내보내기로 처리합니다.

**배움 포인트 — "사용자 입력 → 처리 → 저장" 흐름의 완성**
출결 입력에서 시작해 AI 처리를 거쳐 저장까지 이어지는 운영 흐름이 완성되었고,
CSV 내보내기로 외부(엑셀)와도 연결됩니다.

#### 알려진 동작

이력을 전체 삭제한 뒤 같은 조건으로 리포트를 다시 요청하면,
캐시가 남아 있어 AI를 거치지 않으므로 이력에도 기록되지 않습니다.

- 캐시를 함께 비우면 해결되지만, 그 경우 재생성 시 API 호출이 다시 발생합니다
- 이력 초기화는 드문 동작이고, 출결이 갱신되면 캐시 키가 달라져 자연히 해소됩니다
- **호출 절감을 우선해 현재 동작을 유지**하기로 결정했습니다

### 8-2. 다크 모드 (UX 고도화)

| 항목 | 내용 |
|---|---|
| 구현 방식 | CSS 변수 오버라이드 (`body.dark`) |
| 전환 | 설정 화면의 토글 버튼 |
| 유지 | localStorage에 저장, 재접속 시 복원 |

**CSS 변수를 미리 쓰고 있었기 때문에** 색상 값을 한 곳에서 바꾸는 것으로 전체가 전환됩니다.
개별 요소의 색을 직접 적었다면 수십 곳을 고쳐야 했을 것입니다.

다만 하나의 변수가 배경과 글자 두 역할을 겸하고 있어,
역할별로 변수를 분리하는 작업이 선행되어야 했습니다. (README 개발 로그 참조)

| 시작 시 전체 화면 (v1.7) | 바로가기가 브라우저를 `--start-fullscreen` 으로 실행(설치 때 브라우저 선택·기억). 옵션이 무시된 경우 첫 입력·클릭 때 Fullscreen API로 전환(1회) |
| 화면 자동 맞춤 (v1.7) | 기준 1920×1080(사이드바 숨김 시 폭 1660). 작은 화면은 html에 zoom 적용, 높이는 `100vh / zoom` 으로 보정. 수동 100~70% |
| 복구 검사 | 파일 형식·손상·필수 항목을 검사하고 원인별로 안내 (4-4) |
| 데이터 유지 | 설치·업데이트·제거가 브라우저 저장소를 건드리지 않음. 같은 브라우저면 기존 데이터가 그대로 보임 |

> 미션 기간에 적용했던 Vercel 배포와 방문자 분석(Web Analytics)은 로컬 전용 전환과 함께 제거했습니다.
